## 확인된 후보와 분류

- `src/store.ts` — 기능 수정 후보. 주문 상태와 주문·결제 시도 저장 모델의 정의 위치다.
- `src/payments.ts` — 기능 수정 후보. 결제 요청 처리와 결제 시도 기록이 연결된 위치다.
- `src/orders.ts` — 기능 수정 후보. 주문 생성·조회와 상품 재고 상태가 연결된 위치다.
- `src/admin.ts` — 기능 수정 후보. 관리자 주문 목록과 주문·결제 시도 기반 표시 상태가 연결된 위치다.
- `tests/orders.test.ts` — 검증 변경 후보. 주문·결제·관리자 조회를 통합 테스트하는 현재 보장 위치이며, 상태 변경 동작에는 이를 검증하는 테스트가 필요하다.
- `src/server.ts` — 탐색 전용. 주문·결제·관리자 라우터의 현재 등록 연결을 확인하는 위치이며, 확인된 후보 동작의 직접 책임 파일은 아니다.
- `package.json` — 검사 범위 근거. 테스트와 타입 검사를 실행하는 명령을 정의하는 위치다.

## 제외 범위

| 실패 주문 재결제 | 사람 결정으로 허용하지 않는다. | 실패 주문은 재결제 대상이 아닌 범위를 유지한다. |

## 테스트/검증 계획

### 검증 시나리오

| 시나리오 | 준비 조건 | 행동 | 기대 결과 | 연결된 수정 범위 |
| --- | --- | --- | --- | --- |
| 실패 결제의 상태, 응답, 주문 보존 | 재고가 있는 상품으로 `pending` 주문을 만들고 주문 생성 전 상품 재고와 주문 총액을 기록한다. | 해당 주문에 `FAIL`로 시작하는 유효 카드 토큰으로 결제를 요청한다. | HTTP 402를 반환한다. 실패 정보에 `status`, `amountKrw`, `at`가 있고, `status`는 `payment_failed`, `amountKrw`는 주문 총액이다. | 실패 결제 후 주문 보존 및 실패 응답 |
| 실패 결제 뒤 주문 조회와 재고 | 실패 결제가 처리된 주문과 결제 전 기록한 상품 재고가 있다. | 해당 주문을 단건 조회하고 상품 재고를 확인한다. | 단건 조회가 성공하고 주문 상태는 `payment_failed`다. 주문 생성 전과 비교해 재고가 차감되지 않았다. | 실패 결제 후 주문 보존 및 실패 응답; 결제 성공 시 재고 차감 |
| 결제 성공 시 상태와 재고 변화 | 재고가 충분한 상품으로 새 주문을 만들고 주문 생성 전·후 재고를 기록한다. | 유효한 비실패 카드 토큰으로 결제를 요청한다. | 주문 생성만으로는 재고가 줄지 않는다. 성공 결제 뒤 주문 상태는 `paid`이며 재고는 주문 수량만큼 감소한다. | 결제 성공 시 재고 차감 |
| 관리자 실패 주문 정보 | 실패 결제가 처리되어 보존된 주문이 있다. | 관리자 주문 목록을 조회한다. | 해당 주문이 목록에 포함되고 상태, 실패 금액, 실패 시각이 표시된다. | 관리자 실패 주문 정보 조회 |
| 상태 모델의 범위 | 구현된 주문 상태 정의를 대상으로 한다. | 주문 상태로 `payment_failed`를 사용한다. | `payment_failed`는 유효한 주문 상태다. `refunded`는 이번 기대 결과에 포함하지 않는다. | 실패 결제 후 주문 보존 및 실패 응답; `refunded` 제외 범위 |

재고 부족 차단은 차단 시점과 HTTP 응답 계약이 미결이므로, 현재는 기대 결과를 확정할 수 있는 검증 시나리오에 포함하지 않는다. 재결제, 환불, 재결제 후 관리자 표시·중복 재고 차감은 제외 범위이므로 기대 결과에 포함하지 않는다.
